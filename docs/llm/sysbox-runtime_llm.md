# LLM reference: the sysbox runtime

Human document: `docs/sysbox-runtime.md`. Checks:
`tests/test_llm_in_a_box_sysbox.sh` (labels `SYS1`-`SYS8`).

## Requirements, and what enforces them

| Requirement | Enforced by | Failure it prevents |
|---|---|---|
| Sysbox CE >= 0.7.1 | `lbx`, creation path, after the `sysbox-runc` runtime check: `sysbox-runc features \| grep -q '"time"'` | `OCI runtime create failed: namespace {"time" ""} does not exist` |
| `fusermount3` present | `lbx`, creation path: `command -v fusermount3`, with the test seam `LBX_TEST_FUSERMOUNT3_MISSING` | `failed to pre-register with sysbox-fs` |
| fusermount3 AppArmor override on Ubuntu 25.04+ (`apparmor/fusermount3-sysboxfs` as `/etc/apparmor.d/local/fusermount3`) | not enforced before creation (the denial is only visible when the mount fails); `lbx` prints the `journalctl -u sysbox-fs` command and the install lines when a create fails with the pre-registration error (`session::create_failure_hint`, unit-tested) | `failed to pre-register with sysbox-fs`, with `fusermount3: mount failed: Permission denied` in the sysbox-fs log |
| Any current Docker | not enforced (no minimum exists) | — |

Both launcher checks are creation-time only, matching the existing
"image presence and runtime availability are creation-time concerns" rule: a
box that already exists can still be attached, stopped and destroyed without
the runtime being installed.

### Why the check is on the declaration, not a version string

containerd 2.x (Docker 28+) reads `sysbox-runc features` and strips any
namespace the runtime does not declare. 0.7.0's `linux.namespaces` is
`[cgroup ipc mount network pid user uts]`; 0.7.1's adds `time`. The error names
`time` but the real casualty is the user namespace, which containerd mishandles
while removing `time`. Asserting the declaration asserts the cause and holds
for any build that declares it.

## Ownership model (the part that makes the failure confusing)

- A sysbox box is fake-root: container uid 0 -> unprivileged host uid (this
  host: 165536; `uid_map` = `0 165536 65536`).
- Sysbox applies an **ID-mapped mount** to the rootfs so host uid 0 appears as
  container uid 0. This host has no shiftfs (`sysbox-mgr` logs "Shiftfs module
  found in kernel: no"), so ID-mapped mounts are the only mechanism.
- With the mapping absent, host uid 0 is outside the box's mapped range
  (165536-231071) and the kernel reports the **overflow uid 65534**.
- A setuid binary owned by `nobody` is refused by sudo. The files are correct
  on disk.

## The daemon-restart failure

State machine:

```
box running, sudo OK
  -> sysbox daemons restarted (systemctl restart sysbox | host reboot | package upgrade)
  -> sudo STILL OK            (damage is latent; sysbox-fs logs
                               "Received seccompNotifMsg generated by unknown container: <id>")
  -> box stopped and started again
  -> rootfs id mapping NOT applied
  -> box sees uid 65534 for files the host owns as uid 0
  -> sudo refuses: "owned by uid 65534, should be 0"
```

Upstream behaviour, unchanged in 0.7.1: sysbox-fs keeps per-container state in
memory and loses it for containers that already exist. sysbox's own
troubleshooting guide says an affected container must be recreated. This is
verified on both 0.7.0 and 0.7.1 (phase 0 execution state, section 11d), so
upgrading does not fix it.

`lbx --migrate` is the recreate that keeps the box's work: it rebuilds the
container and carries `/home/agent` across (see sysbox-migration_llm.md).

## Launcher implementation

`lbx`:

| Function | Role |
|---|---|
| `sysbox_box_damaged <session>` | Predicate. Returns 0 only when the box is provably damaged |
| `sysbox_box_damage_report <session>` | Prints the cause and the remedy to stderr |

`sysbox_box_damaged` returns 1 (healthy) unless ALL hold:

1. `docker container inspect -f '{{.HostConfig.Runtime}}'` = `sysbox-runc`
2. `docker inspect -f '{{.State.Status}}'` = `running`
3. `docker exec -u 0 <session> stat -c '%u' /etc/sudo.conf` prints something
4. that something is not `0`

Design constraints, each deliberate:

- **No privileges.** An earlier draft compared the box's view against the
  host's view through `/proc/<pid>/root`, which needs root. The launcher never
  uses sudo, so the check uses the box's view alone. The box's view is
  sufficient: a healthy box reports 0.
- **Fails toward "healthy".** Any unreadable state (not running, exec failed,
  empty output) returns 1. The check must never refuse a box it cannot prove
  is damaged — the cost of a false refusal is higher than a missed report.
- **Runtime-gated.** A `docker`-runtime box has no user namespace and no ID
  mapping, so the check is a no-op there.

Call sites (both refuse with exit 1, so no terminal is handed over):

- the `running)` branch of the state dispatch, before `attach_session`
- the `exited|created)` container branch, after `wait_for_running` and before
  `attach_session`

The `missing)` (creation) branch does not call it: a box being created cannot
yet be damaged, and the id mapping is established at create time.

## Entrypoint idempotency

`entrypoint.sh` renames the login from `agent` to `$HOST_USER` on start. The
rename can only happen once, so the block is guarded:

```bash
if [ "$TARGET_USER" != "agent" ] && ! id "$TARGET_USER" >/dev/null 2>&1; then
    ... usermod -l / sed fallback / useradd fallback ...
fi
```

Without the `! id "$TARGET_USER"` guard, a restart tries to rename a user that
no longer exists: `usermod -l` fails, the `sed` fallback matches nothing, and
the container logs `entrypoint: usermod -l failed, falling back to sed rename`
on every start after the first.

**Measured, and it matters for the tests:** that failure line is the bug's ONLY
observable effect. The box's user, `/etc/sudoers.d/agent` and sudo all survive
it, because the block's final existence check passes anyway. A check that
asserted only the identity state would pass on the buggy code — measured
2026-10-11. The red assertion is therefore the log delta per cycle.

The sudoers write stays outside the guard and runs on every start with
`TARGET_USER != agent`, so it is repaired if lost and its content is
deterministic.

## Test map

| Label | Red/green | What it asserts |
|---|---|---|
| SYS1 | green pin | `sysbox-runc features` declares `time` |
| SYS2 | red | launcher refuses without `fusermount3`, naming fuse3 |
| SYS2 (control) | green pin | no false report when `fusermount3` is present |
| SYS8 | green pin | a box launches on the host's current Docker |
| SYS3 (precondition) | green pin | sudo works on a fresh box |
| SYS3 (ground truth) | green pin | after the trigger the box sees 65534 and sudo fails |
| SYS3 (verdict) | red | launcher refuses, exits non-zero, names cause and remedy |
| SYS4 | green pin | the remedy works; a recreated box is not refused |
| SYS5 | green pin | healthy box not reported after stop/start and kill/start |
| SYS6 | red | a second start logs no new rename failure |
| SYS6 (identity) | green pin | `/etc/passwd`, `/etc/group`, `/etc/sudoers.d/agent` byte-identical |
| SYS7 | red | no cycle re-runs the rename (log delta does not grow) |
| SYS7 (identity) | green pin | user, sudoers and sudo intact across cycles |

Assertion-design notes that are easy to get wrong:

- **Use the numeric `docker exec -u 1000:1000` form in sudo checks.** The name
  form (`-u <name>`) fails with `unable to find user` on a box whose
  `/etc/passwd` cannot be resolved in the outer daemon's context, which makes a
  check pass or fail for the wrong reason.
- **Damage assertions must not match the launcher's normal banner.** Every
  healthy launch prints `... — sysbox runtime; enables bridged VM networking`,
  so a bare `/sysbox/` or `/restart/` pattern passes on an undamaged box.
  Measured: an early SYS3 did exactly this. The patterns now require
  damage-specific wording (`damaged|65534|id.?mapping|owned by uid`, a
  daemon-word paired with a restart-word, `destroy|recreate`).
- **SYS3 asserts the ground truth before the verdict**, so the launcher's
  answer cannot be right by accident.
- **SYS4's positive control is what stops SYS3 passing trivially**: without it,
  a launcher that refused every box would pass SYS3.

## Out of scope

- `--disable-idmapped-mount` on `sysbox-mgr`: would suppress the mapping
  entirely, weakening ownership translation for every box on the host. Not
  used. See the plan's out-of-scope section.
- The sysbox image's **inner** Docker pin (`docker-ce` 27.5.x,
  `containerd.io` 1.7.28): that is the Docker-in-Docker daemon inside the box,
  a separate decision from the host's Docker, and it is unchanged.
- The 9p `/data` share: sysbox cannot apply an ID-mapped mount to a 9p
  filesystem, which is why the runtime logs a warning about `/data` in a `vm`
  box. Not a defect on a real sysbox host, where `/data` is a bind mount on
  ext4.
